**进行中：** v1.0.4 已发布；仓库已公开。安装脚本结尾的总结信息此前会把地址位置原样打印成 `<this-server>` 占位符，导致其中每个 URL 在使用前都得手动改一遍。现在它会显示真实地址：内核用来离开该机器的源地址会出现在公开页面和控制台的行里；在多网卡机器上，其余地址会在下方逐一列出，各自标注所属接口。检测失败时会回退到旧的占位符，而不会导致安装失败。已在一个一次性的 systemd 容器中做了端到端验证，该容器额外挂载了第二块网卡：三种语言全部对齐，每个打印出的地址都以 HTTP 200 响应，且被打桩替换掉的 `ip` 命令仍然以 0 退出。更早的补丁，按时间从新到旧排列：v1.0.3 让 `install_iperf3()` 把“更新再安装”这一整对操作一起重试（`apt-get update` 报告成功后，过期的 `security.debian.org` 索引仍可能导致安装 404），并补上了 README 中未填写的 `<repo-url>`/`v0.1.0` 安装占位符；v1.0.2 修复了 `install_iperf3()` 在一个不相关的 apt 源导致 `apt-get update` 失败时会整个跳过安装的问题；v1.0.1 修复了 CHANGELOG 中维护者注释在更新日志页面上的渲染问题——仅影响显示效果，其余不受影响。

在 v1.0.0 之前，运维人员已在真实主机上验证了每一项功能：公开页面在两个公开端口上均可响应，控制台和浏览器测速均正常工作，iperf3 测速窗口在局域网内测得 2.8 Gbit/s，并在窗口关闭后自行拒绝连接，anytls 节点可正常安装、轮换凭据并干净地拆除，升级操作能够在不影响该节点的情况下重放已记录的设置，且三种界面语言均能正常渲染。目前没有正在进行中的工作。
**下一步：** 决定是否需要把共享的 `_db_lock` 解耦——每次命中公开页面都会占用一把进程级的锁并执行一次同步的 SQLite 写入，而控制台也共用这把锁，因此理论上匿名流量的高并发有可能拖慢已认证页面的响应速度。**已实测但未能复现**：60 个并发的高频请求下，控制台延迟保持在 0.4–0.6 毫秒，与空闲状态一致。之所以记录下来，是为了避免这个机制日后被当作新问题重新发现；在没有能证明其确有危害的实测数据之前，不要为此重新设计架构。
**已知问题：** 没有会破坏功能的问题。`BACKLOG.md` 中有四项是主动选择保留、而非缺陷：一是共享的 SQLite 锁，其所报告的负载影响未能复现；二是启动和关闭时的两处信号边界情况；三是单独设置 `VPSSRV_MODULES=iperf3` 时不会安装任何东西；四是缺少登录限速。
**阻塞于：** 无。
