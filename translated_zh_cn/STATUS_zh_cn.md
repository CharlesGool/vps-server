`install_iperf3()` 把 `apt-get update && apt-get install iperf3` 串在一起执行，并丢弃了全部
输出，结果一个与之无关的、已损坏的 apt 源（在某台真实 VPS 上实测出现过）会让
整个安装步骤悄无声息地被跳过。现已修复：重试 update，无论 update 本身
结果如何都会尝试安装，并且不再隐藏 apt 的报错输出。已在一个一次性的、
启用了 systemd 的 Debian 12 容器（并非这台正式主机）中，针对同样的已损坏 apt 源场景，
完整跑通一次端到端的 `install.sh` 并验证：iperf3 安装成功，`vps-server-web.service`
处于 active 状态，控制台和公开监听端口均返回 HTTP 200。v1.0.1 修复了
CHANGELOG 页面上维护者注释的渲染问题——仅影响显示，其他方面未受影响。

**下一步：** 决定是否需要解耦共享的 `_db_lock`——目前每次公开页面的访问
都会占用一个进程级的锁并同步写入 SQLite，而控制台也共用这把锁，
因此理论上匿名的高频请求有可能拖慢已认证页面的响应。**已实测但未能复现**：60 个并发
高频请求源下，控制台延迟保持在 0.4–0.6 毫秒，与空闲时相同。记录在此是为了
避免这个机制以后被当作新问题重新发现；在没有测量数据证明存在实际危害之前，不要
重新架构它。
**已知问题：** 没有任何会破坏功能的问题。`BACKLOG.md` 中有四项属于
