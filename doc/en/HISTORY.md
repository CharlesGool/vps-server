## Earlier English design notes (pre-v5.0.0 snapshot)

The paragraphs below preserve design detail removed from the current English translation during source alignment. Treat them as a dated snapshot, not current instructions.

The Changelog remains available as a permanent Home and Settings entry. Its
card has no switch, and module actions cannot disable it. The iperf3 window
offers basic, one-stream, and four-stream commands without requiring JSON
output; the first two use the same stream count by design.

The later module page requires the same short-lived administrator verification
as other Security Settings. It submits only fixed module names and actions to
a separate privileged systemd job. The job records progress outside the Web
service, allowing a Web restart during installation. Disabling a proxy module
does not remove its nodes or credentials; disabled units remain stopped when
node controls are used. The iperf3 and public listener switches restart the Web
service to apply their settings. HTTP and HTTPS have separate persisted flags;
when a flag does not yet exist, it inherits the former combined public-page
flag or the installation default. The control panel stays available on its
separate listener.

The visitor database, `portfwd.json` (enabled forwarding rules), and
`login-access.json` (private-IP allowlist) persist under `$VPSSRV_DATA_DIR`.
An optional `server-label.txt` in that directory stores the operator's
server identifier. The ordinary Settings page edits it with a CSRF-protected
form; the shared page renderer reads it for the top-left label and browser
title without restarting Web. Empty input clears the label.
`console_port.txt` stores the generated console port. An authenticated Settings
action starts a privileged port-change job that checks listeners and the host
port registry, writes `data/console-port-override`, restarts Web, verifies the
new listener, and restores the old port and registry on failure. The host
registry is the host port registry; the console records its listener there.
The signed-in Settings page owns the four installable modules: iperf3,
Singbox, FRPS, and FRPC. HTTP page (80) and HTTPS page (443) each have
their own card and switch on Home. Selecting an enabled Home card opens its public
listener; selecting a disabled one shows the closed page. The Web process
records which listeners actually bound. The privileged switch helper checks
that report after restart, restores the previous flag on failure, and reports
a port conflict on the relevant card. The console remains available on its
separate port.
An in-place install also stages the version-matched source needed for later FRPC setup.
Optional installs and uninstalls run through the serialized root helper;
`data/module-job.json` exposes its state and `data/module-job.log` contains
the complete latest installer output, including live apt progress. Singbox and
FRPS install from bundled binaries, while apt installs system dependencies.
Singbox installation creates validated empty configurations for its two
services; operators add nodes explicitly in the console. Existing
configurations are validated and preserved on upgrade.
The Modules action installs both Singbox services in one installer run so
their configurations enter the node inventory before either service starts.
FRPS installation uses its own setup script and retains the FRPS configuration file
on uninstall, avoiding an unrelated traffic-meter restart and keeping clients'
server port and token stable after reinstall.
Uninstalls
archive current module configuration under `data/` before removing it.
Removing Singbox also reconciles its node inventory and stops the traffic
meter. Reinstalling a removed node module preserves an inventory backup,
then imports the newly installed configuration. Installing an unrelated
module does not require the traffic meter when no node module is selected.
During a node install, the installer stops node services and defers their
restart until both configuration files have been imported into the inventory
and the traffic meter is ready. Enabled node services then start again.
Home keeps one switch for each function except Settings. Built-in feature
flags persist under `data/`; the Port forward flag is reconciled by the running
Web process so its saved rules are withdrawn or reapplied without invalidating
console sessions. Disabled feature routes lead to a localized closed page.
Module action forms accept one submission per page load, and concurrent jobs
return to the requesting page. The FRPC group
flag saves the names of running instances before stopping them and restores
only those instances when re-enabled. The Proxy nodes group controls the
AnyTLS and proxy units while the node inventory stays intact.
Home opens FRPS at `/frps` and the FRPC instance list at `/frpc`; the client
editor remains under `/frp/client/edit`. The former combined `/frp` route
redirects to the FRPC list for existing bookmarks.
FRPC instance names allow normalized Unicode letters and numbers plus `_` and
`-`, up to 32 characters. The canonical configuration keeps that name in
`/etc/frp/frpc-<name>.toml`. Existing ASCII names keep their systemd unit names;
Unicode names use a stable ASCII unit name and a root-owned configuration
symlink because the `frpc@.service` template expands `%i` into its config path.
The client list excludes these aliases. Creating, renaming, or deleting an
instance maintains its alias, and a failed create removes both files.
The console password, selected port, web certificates and
`.install-state` live under `$PREFIX`; the sing-box module configs and their
certificates live in `/etc/vps-server-anytls/` and `/etc/vps-server-proxy/`.
See [Paths & mounts][local-link-012]. The iperf3 deadline stays in memory
and does not survive restart.

## Retired anytls console path

The following design record describes historical behavior. Console calls to `POST /anytls/reset` and the old installer script were removed from current code.

### The console's anytls section

**On `/proxy` rather than a separate page** (2026-09-22): anytls and proxy protocols shared one page. `/anytls` redirected to `/proxy`, while `POST /anytls/reset` remained at the time. Only the standalone `GET /anytls` page, navigation link and Dashboard tile were removed. The following described the anytls portion of that combined page.

The console read the installed node from `VPSSRV_ANYTLS_CONFIG` and rendered its status, a ready-to-paste Clash entry and an `anytls://` link. Its only write action was Reset port and password, delegated to `setup-anytls.sh reset`; the console did not edit `config.json`. The script withdrew the old port's firewall rule before opening the new port to avoid leaving an unused `ACCEPT` rule. A server-validated confirmation checkbox guarded the reset because credential rotation broke configured clients until their new credentials were distributed; the HTML `required` attribute alone did not protect against nonbrowser clients.

The reset ran **outside the long-running Web sandbox**, using `systemd-run --pipe --wait --collect` as a transient unit. With `ProtectSystem=strict` and only `ReadWritePaths=$PREFIX`, the Web unit could not write `/etc/vps-server-anytls` or a unit file. The first real attempt failed halfway through for that reason after withdrawing the old firewall rule. Widening `ReadWritePaths` to `/etc/systemd/system` would have granted a permanent write permission for one action. Where `systemd-run` was unavailable, the script ran directly, matching environments where `install.sh` omitted hardening. `setup-anytls.sh reset` checked writability before touching the firewall so a failure would not strand a running but unreachable node.

The node password was shown in clear text within the authenticated `ConsoleHandler`; `ProbeHandler` had no route to it, and a historical test asserted that the public listener returned 404 for `/anytls` without leaking the password. The server address came from the request's `Host` header rather than an outbound IP lookup; an operator needing another address edited the copied line. SNI was not stored in the sing-box configuration: `setup-anytls.sh` baked it into the self-signed certificate's CN, from which the console read it back.

Only a verified administrator could view or change Security Settings. The allowlist accepted individual RFC 1918 private IPv4 or unique-local IPv6 addresses, rejected public IPs and ranges, and had a separate enable switch. Passwordless admission used the connection peer rather than client forwarding headers; `VPSSRV_TRUST_PROXY=1` disabled it because no trusted-proxy boundary was configured. An allowed visitor chose IP access on Login, received an IP-bound session, and was rechecked against the list and switch on each request; removal or disabling took effect on the next request. Ordinary console pages were accessible, while Security Settings required a fresh administrator-password challenge with a fixed 10-minute permission and renewed password session. A password change invalidated prior sessions. Devices mapped through one allowed private gateway IP shared that access. Ordinary appearance and language settings required no repeated password challenge.

## Retired proxy-console reset path

This earlier design delegated `setup-proxy.sh reset` from the console. The current page uses only the managed-node helper; the terminal script's behavior was not changed by this code cleanup.

The console's `/proxy` page formerly showed each installed node's port, UUID or password, per-node SNI read from its certificate, and Clash entries and share links (`vmess://`, `vless://`, `trojan://`, `ss://`) for detected addresses. **Each protocol had its own reset button.** The operator rejected a combined reset because one leaked vmess UUID should not require reconfiguring trojan, vless and shadowsocks clients. `setup-proxy.sh reset <protocol>` rotated only that protocol's port and credential; `load_installed_vars()` read the other protocols' values from disk first. Bare `reset` still rotated all installed protocols for terminal or script use but was absent from the console. Both forms ran via sandbox-external `systemd-run`, as did `anytls_reset()`, because of `ProtectSystem=strict`. Sharing one systemd service meant that even a one-protocol reset briefly dropped other protocols' connections, though their credentials remained unchanged.
