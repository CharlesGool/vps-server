**進行中：** v1.0.3 已發布；此儲存庫為公開。v1.0.2 的 iperf3
安裝修復並不完整：`apt-get update` 可能回報成功，但
`security.debian.org` 的 CDN 卻回傳一份過期的索引，使下一次的
`apt-get install` 出現 404 —— 這在真實主機上把 v1.0.1 升級到 v1.0.2 時
確實發生過。`install_iperf3()` 現在會重試整組 update-then-install，
而不只是重試 update。同時也修好了 README 的 `## Install` 章節，
該章節自 v1.0.0 起就一直留著未填寫的範本佔位符（`<repo-url>`、
一個此專案從未有過的範例 `v0.1.0` 標籤）。已在一個可拋棄、
啟用 systemd 的 Debian 12 容器（非此真實主機）中，
以相同的損壞儲存庫情境進行完整的端對端 `install.sh` 驗證：
iperf3 安裝成功、`vps-server-web.service` 啟動並處於 active 狀態，
且控制台與公開監聽埠皆回應 HTTP 200。v1.0.2 修復了
`install_iperf3()` 在某個不相關的 apt 儲存庫導致
`apt-get update` 失敗時，會整個跳過安裝的問題；v1.0.1 修復了
CHANGELOG 頁面上維護者留言的顯示問題 —— 僅影響顯示，
其餘不受影響。

在 v1.0.0 之前，每項功能都已由操作者在真實主機上驗證過：
公開頁面在兩個公開埠上皆能回應、控制台與瀏覽器測速功能正常、
iperf3 視窗在區域網路內測得 2.8 Gbit/s，且在視窗自行關閉後
會拒絕連線、anytls 節點可正常安裝、輪替憑證並乾淨地拆除、
升級會重放已記錄的設定而不影響節點，且三種介面語言皆能正常
呈現。目前沒有任何工作正在進行中。
**下一步：** 決定是否需要將共用的 `_db_lock` 解耦 —— 每次
公開頁面的存取都會取得一個行程層級的鎖，並執行同步的
SQLite 寫入，而控制台也共用這個鎖，因此理論上匿名的洪水式
存取可能拖慢已驗證使用者的頁面。**已測量但未能重現**：
60 個並行洪水式存取者的情況下，控制台延遲維持在 0.4–0.6 ms，
與閒置時相同。記錄下來是為了避免這個機制之後被當成新問題
重新發現；在沒有能證明有害的測量結果之前，不要重新架構。
**已知問題：** 沒有任何會造成破壞的問題。`BACKLOG.md` 中有四項
是刻意保持開放，而非因為有缺陷：一個共用的 SQLite 鎖，其回報的
影響在負載測試下無法重現；兩個啟動與關閉訊號的邊界情況；
單獨設定 `VPSSRV_MODULES=iperf3` 卻不會安裝任何東西；以及
尚未實作登入速率限制。
